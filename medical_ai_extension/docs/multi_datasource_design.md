# 医疗多源数据测试设计说明

本文档用于说明在智慧医疗与医疗 AI 应用场景下，接口自动化测试框架如何扩展支持多源异构数据的测试准备、结果校验和数据清理。

## 1. 设计背景

医疗 AI 应用通常不仅包含模型推理接口，还依赖多类医疗数据：

- 结构化临床数据；
- 非结构化病历文本；
- 高频生命体征或生物信号数据；
- 模型特征、任务状态和热点数据缓存。

因此，接口自动化测试不应只校验 HTTP 响应，还需要关注接口返回结果与后端数据状态之间的一致性。

## 2. 数据源职责划分

| 数据源 | 医疗场景示例 | 测试用途 |
| --- | --- | --- |
| MySQL | 患者基本信息、检验指标、诊断编码、住院记录 | 测试前置数据准备、接口结果落库校验、测试后数据清理 |
| MongoDB | 电子病历文本、影像报告、医生诊疗记录 | 半结构化文档准备、文本类接口输入与结果校验 |
| Redis | token、任务状态、热点患者特征、模型配置缓存 | 缓存命中测试、缓存失效测试、测试 key 清理 |
| ClickHouse | 生理信号特征、ETL 分析宽表、批量统计结果 | 大规模分析型查询、模型输入特征统计校验 |

## 3. 测试数据隔离策略

为了避免污染测试环境，建议所有自动化测试数据都使用统一标识：

- `patient_id` 使用 `TEST_` 前缀；
- Redis key 使用 `test:medical:` 前缀；
- MongoDB 文档增加 `test_case_id` 字段；
- ClickHouse 写入数据增加 `batch_id` 字段；
- MySQL 表中增加可追踪的测试批次号或测试患者编号。

## 4. 前置准备与后置清理

### 4.1 前置准备

1. 清理同名历史测试数据；
2. 插入当前测试所需的患者信息、检验指标或病历文本；
3. 根据测试目标决定是否预置 Redis 缓存；
4. 调用被测接口。

### 4.2 后置清理

1. 删除 MySQL 中 `TEST_` 前缀患者数据；
2. 删除 MongoDB 中对应 `test_case_id` 文档；
3. 删除 Redis 中 `test:medical:` 前缀 key；
4. 删除或标记 ClickHouse 中对应 `batch_id` 的测试数据。

## 5. 结果一致性校验示例

以疾病预测接口为例，接口返回结果后可以进行如下校验：

1. HTTP 响应状态码是否符合预期；
2. 返回 JSON 是否包含 `request_id`、`model_version`、`risk_level`、`probability`；
3. `probability` 是否在 `[0, 1]` 范围内；
4. `risk_level` 是否属于 `low / medium / high`；
5. 如果接口会写入预测记录，则查询 MySQL 或 ClickHouse 判断记录是否存在；
6. 如果接口会写入任务状态，则查询 Redis 判断任务状态是否正确。

## 6. 面试说明建议

该设计可以作为简历项目中的扩展点说明，但不建议表述为已经完整接入真实医院生产数据库。更稳妥的说法是：

> 我结合医疗数据特点，设计了多源数据在接口自动化测试中的使用方案，包括前置数据准备、接口结果校验和测试后清理。目前该部分主要用于个人项目的场景化扩展，后续可以继续补充真实数据库连接与统一连接池管理代码。
